# GuildFrontierSim 開発指示・基本設計

## 1. このドキュメントについて

本書を GuildFrontierSim のメイン開発指示とする。

実装前に本書と関連ドキュメントを確認し、一度に全機能を作らず、記載したフェーズ順に小さく実装・検証する。既存コードがある場合は、プロジェクト構造と現在の実装を確認してから変更する。

関連ドキュメント：

- [ComfyUI キャラクターグラフィック生成・連携設計](./ComfyUICharacterGraphicsIntegration.md)

---

## 2. プロジェクト概要

Unity で「冒険者ギルド経営＋RPG 戦闘」のシミュレーションゲームを制作する。

プレイヤーはギルドに所属するキャラクターの一人として開始する。状況によってはギルドリーダーとなり、経営、人員配置、遠征などを指示する。プレイヤーがリーダーではない場合やリーダーがギルドを離れている場合は、CPU がギルド経営を行う。

最終的には次の要素を組み合わせる。

- ギルド経営シミュレーション
- キャラクター管理
- 防衛戦
- 遠征
- 自動戦闘
- コマンド RPG 戦闘
- リーダー交代
- CPU によるギルド経営
- キャラクターメイク
- NPC スカウト
- ComfyUI を利用したキャラクターグラフィック制作

最初からすべてを実装しない。まず「経営部分＋自動処理」だけでゲームサイクルが成立するプロトタイプを作る。

---

## 3. 基本ゲームサイクル

基本的に次の流れを繰り返す。

1. ギルドの状態を確認する。
2. 防衛・遠征にメンバーを割り当てる。
3. 防衛戦や遠征を処理する。
4. 資金・アイテムなどを獲得する。
5. キャラクターの負傷・虜囚・離脱などを処理する。
6. 給料などの維持費を支払う。
7. 次のターンへ進む。

初期実装では戦闘を画面上で行わず、ステータスから結果を計算する自動戦闘とする。

---

## 4. ギルド

ギルドは最低限、次の情報を持つ。

- ギルド名
- 所持資金
- 所持アイテム
- 所属キャラクター一覧
- 現在のリーダー
- 代理ギルド長
- 虜囚になっているキャラクター
- 入院・休業中のキャラクター

将来追加できる情報：

- ギルドランク
- 評判
- 拠点設備
- 病院
- 訓練施設
- 倉庫
- 雇用可能人数

---

## 5. キャラクター

キャラクターは最低限、次の情報を持つ。

- ID
- 名前
- レベル
- HP
- 攻撃力
- 防御力
- 素早さ
- 給料
- ギルド忠誠度
- 状態
- リーダーかどうか
- プレイヤーキャラクターかどうか

状態は最低限、次を表現できるようにする。

- `Available`
- `Expedition`
- `Defending`
- `Injured`
- `Hospitalized`
- `Captured`
- `Resting`

### 5.1 忠誠度

キャラクターごとにギルド忠誠度を持つ。初期値はおおむね 10～50 とする。

忠誠度が `-100` 以下になると、そのキャラクターは原則としてギルドから離脱する。将来は次の要因で変化させられるようにする。

- 給料未払い
- 戦闘結果
- 仲間の死亡
- リーダーとの関係
- ギルドの評判

### 5.2 キャラクター画像

キャラクターの戦闘・経営データと画像アセットを分離する。キャラクターは安定した `visualId` などの論理参照を持ち、画像が見つからない場合は既定画像を表示する。

画像生成は Unity 内で行わない。独立した WPF ツールから ComfyUI を利用し、採用済み画像とメタデータを Unity へ取り込む。詳細は関連ドキュメントを参照する。

---

## 6. 防衛戦

一定確率またはイベントによって、モンスターがギルドや周辺地域へ来襲する。防衛戦では参加キャラクターを決定する。

### 6.1 手動選択

リーダーがギルドにいる場合、プレイヤーが防衛キャラクターを選択できる。単独でも複数でも参加可能とする。

### 6.2 自動選択

次の場合は CPU が防衛メンバーを選ぶ。

- リーダーがギルドにいない
- プレイヤーが自動選択を指定した

将来は代理ギルド長の能力によって選択傾向を変えられるようにする。

### 6.3 防衛戦結果

#### 勝利

- 防衛成功
- 資金獲得
- アイテム獲得

#### 敗北するが撃退成功

- 防衛成功
- 資金獲得
- アイテム獲得
- 報酬は通常勝利より少ない
- 一定確率でキャラクターが重傷になる

重傷者は `Hospitalized` または `Resting` となり、一定期間活動できない。将来「完全な防衛失敗」も追加できる設計にする。

---

## 7. 遠征

ギルドメンバーを選択し、特定地域へ遠征させる。開始時に参加キャラクターと遠征先を決める。

リーダーがギルドにいる場合は手動選択できる。リーダー不在または自動設定の場合は CPU が選択する。

### 7.1 遠征の進行

遠征は複数ステージを進む方式とする。

```text
Guild
  ↓
Area 1
  ↓
Area 2
  ↓
Area 3
  ↓
Boss
```

各エリアで戦闘が発生する可能性がある。戦闘後は「さらに奥へ進む」または「ギルドへ帰還する」を決める。CPU 操作時は自動判断する。

### 7.2 遠征中の戦利品

遠征中に次を獲得できる。

- 資金
- アイテム
- 虜囚となっているキャラクター

これらは遠征中の一時的な戦利品として管理し、無事にギルドへ帰還した時点で正式にギルド資産へ追加する。

### 7.3 遠征戦闘結果

#### 勝利

- 資金獲得
- アイテム獲得
- 虜囚キャラクターを救出できる可能性がある
- 先へ進むか帰還するかを決定する

#### 敗北するが逃走成功

- 一部の資金・アイテムを保持する
- 勝利時より報酬が少ない
- キャラクターが負傷する可能性がある
- 一部の虜囚を救出できる可能性がある
- 遠征終了

#### 敗北して逃走にも失敗

遠征メンバーは `Captured` となり、一時的に利用できなくなる。別の遠征隊が救出することで復帰できる。

---

## 8. 虜囚システム

虜囚になったキャラクターは死亡扱いにせず、データを残して `Captured` 状態にする。

Captured 状態では次の制限を受ける。

- 防衛参加不可
- 遠征参加不可
- 給料処理は将来調整
- 救出対象として遠征先に登場可能

これにより「前回全滅した遠征隊を別のパーティーで救出する」という展開を可能にする。

---

## 9. リーダーシステム

ギルドには原則として必ず一人のリーダーが存在する。

### 9.1 リーダーがギルドにいる場合

プレイヤーがリーダーなら、次の判断を行える。

- 防衛メンバー選択
- 遠征メンバー選択
- 遠征先選択

### 9.2 リーダー不在の場合

リーダーが遠征中、入院中、虜囚などで不在の場合、代理ギルド長が経営を担当する。代理ギルド長が存在しない場合は、利用可能なメンバーから自動選択する。

### 9.3 リーダー交代

現在のリーダーが虜囚、長期離脱、その他の継続不能状態になった場合、残りのメンバーから新しいリーダーを選ぶ。

プレイヤーに選択権があれば手動選択し、それ以外は CPU が選択する。将来は次の情報をリーダー選択 AI に利用できるようにする。

- 忠誠度
- レベル
- 戦闘能力
- 指揮能力
- 在籍期間

---

## 10. 戦闘システム

### 10.1 自動戦闘

初期戦闘システムは単純な数値計算とする。

```text
PartyPower = 各キャラクターの戦闘力の合計
EnemyPower = 敵側戦闘力
```

ランダム補正を加えて勝敗を決め、`BattleResult` として結果を返す。

- `Victory`
- `DefeatButRepelled`
- `Escape`
- `Capture`

戦闘の勝敗計算と、その結果を防衛・遠征へ適用する処理を分離する。`BattleResolver` と `DefenseBattleResultProcessor`、`ExpeditionBattleResultProcessor` などに責務を分ける。

### 10.2 将来のコマンド RPG 戦闘

リーダーまたはプレイヤーキャラクターが防衛戦・遠征へ直接参加した場合、将来的にコマンド RPG 形式の戦闘を発生させる。参加していない戦闘は自動計算する。

初期プロトタイプではリーダー参加時も含め、すべて自動戦闘でよい。将来の操作戦闘も、終了後に共通の `BattleResult` を経営側へ返し、経営システムと密結合させない。

---

## 11. 給料

一定ターンまたは一定日数ごとに、ギルドメンバーの `Salary` 合計をギルド資金から支払う。

資金不足時は忠誠度低下や離脱リスク増加を発生させる。具体的な数値は固定せず、Inspector または設定データから調整できるようにする。

---

## 12. キャラクター加入

### 12.1 登録

キャラクターメイクによって新しい冒険者を作成する。

### 12.2 スカウト

既存 NPC と会話、イベント、戦闘、共闘などを行って好感度を上げ、一定以上になるとギルドへ勧誘できるようにする。

キャラクターメイクとスカウトは初期プロトタイプでは実装しない。

---

## 13. ゲーム開始パターン

将来的に三種類程度の開始方法を用意する。

### Pattern A：既存ギルド

最初から一定規模のギルドが存在し、プレイヤーは一般メンバーとして開始する。序盤はギルドから指示された防衛、遠征、クエストをこなし、ゲームに慣れてから経営へ関われるようになる。

### Pattern B：弱小ギルド

メンバーが少なく弱い、資金も少ない廃れたギルドから開始する。比較的早くリーダーになれる。初期プロトタイプではこのパターンを使用する。

### Pattern C：新規設立

ギルド設立から開始し、プレイヤーが最初からリーダーとなる。自由度は高いが、初期メンバーのキャラクターメイクなどが必要になる。

---

## 14. CPU ギルド経営

プレイヤーが一般冒険者として活動している間も、CPU がギルドを経営できるようにする。

CPU の判断対象：

- 防衛メンバー選択
- 遠征メンバー選択
- 遠征先選択
- 遠征継続判断
- 帰還判断
- リーダー選択

最初はルールベースで実装する。

- HP が低いキャラクターは遠征させない
- 負傷者は選択しない
- 強いキャラクターを優先する
- ギルド防衛用に最低人数を残す
- 遠征で一定以上の戦利品を獲得したら帰還する

判断部分は独立したクラスにし、後からアルゴリズムを変更できるようにする。

---

## 15. Unity UI 方針

Unity の GUI を完全にコード生成しない。可能な限り次の要素を Unity Editor 上で配置する。

- Canvas
- Panel
- Button
- TextMeshPro
- ScrollView
- LayoutGroup
- Prefab

大量の GameObject を生成する UI コードは避ける。必要な Hierarchy 構成を README またはセットアップドキュメントへ記載し、UI スクリプトは Inspector から参照を設定できる形にする。

キャラクターグラフィック生成 UI は Unity UI の対象外であり、独立した WPF ツールとして実装する。

---

## 16. データ設計

ゲームバランス用データをコードへ大量にハードコードしない。可能なものは ScriptableObject 化する。

候補：

- `CharacterDefinition`
- `EnemyDefinition`
- `ExpeditionAreaDefinition`
- `GuildStartingPreset`
- `BattleBalanceSettings`

プレイ中に変化する次の情報はランタイムデータとして管理する。

- HP
- 忠誠度
- 負傷状態
- 所持金
- 虜囚状態

ScriptableObject 自体を書き換えてゲーム状態を保存しない。マスターデータとランタイム状態を分離し、将来のセーブ・ロードを考慮する。

---

## 17. ComfyUI と WPF キャラクターグラフィックツール

キャラクター画像の生成、候補比較、採用、履歴管理は Unity 内で行わず、`Tools/` 配下に作成する独立した WPF ツールで行う。

基本的な責務分担：

```text
WPF Tool                         Unity
  外見指定                         採用済み画像のインポート
  Prompt / Workflow 構築           visualId とアセットの関連付け
  ComfyUI HTTP API 通信            キャラクター画像の表示
  候補比較・採用                    欠損時の既定画像表示
  画像・メタデータ出力
```

Unity は ComfyUI へ直接接続しない。WPF ツールは採用画像と `character-visual.json` を出力し、Unity はそれらを検証して取り込む。

この機能は Phase 1 の必須範囲へ含めない。Phase 1 ではキャラクター ID を安定させ、画像未設定時に既定画像を利用できる境界だけを意識する。本格的な統合は Phase 5 で行う。

詳細な構成、保存形式、セキュリティ、テスト、導入手順は [ComfyUI キャラクターグラフィック生成・連携設計](./ComfyUICharacterGraphicsIntegration.md) に従う。

## 18. 実装フェーズ

### Phase 1：経営自動シミュレーション

最優先。次を実装する。

- GuildManager
- Character runtime data
- ギルド資金
- 給料
- 忠誠度
- 防衛戦
- 遠征
- 自動メンバー選択
- 自動戦闘
- 負傷
- 虜囚
- 帰還
- リーダー
- リーダー交代
- ターン進行

この段階では、ボタンを押してターンを進めるだけでもよい。まず「CPU に任せて放置してもギルドの状態が変化し続ける」ところまで作る。

### Phase 2：手動経営

Phase 1 が動作してから実装する。

- 防衛メンバー手動選択
- 遠征メンバー手動選択
- 遠征先手動選択
- 遠征継続・帰還選択
- 代理ギルド長設定
- リーダー選択
- 経営 UI

### Phase 3：プレイヤー冒険者モード

CPU が経営を担当し、プレイヤーがギルド所属冒険者として活動できるようにする。

- CPU からクエストを割り当てられる
- プレイヤーが防衛・遠征へ参加する
- プレイヤーが一般メンバーとして生活する
- CPU リーダーが経営判断する

### Phase 4：コマンド RPG 戦闘

リーダーまたはプレイヤーキャラクターが参加する戦闘を実際に操作できるようにする。経営システムと戦闘システムを密結合せず、戦闘終了後に `BattleResult` を経営側へ返す。

### Phase 5：キャラクター・イベント拡張

- キャラクターメイク
- NPC
- 会話
- 好感度
- スカウト
- 共闘イベント
- イベント戦闘
- WPF ツールで作成したキャラクター画像の本格統合

## 19. Phase 1 の最低完了条件

まず Phase 1 のみを実装し、Phase 2 以降を先取りしない。最低限、次の状態まで作る。

1. 数人のギルドメンバーが存在する。
2. ギルドに資金が存在する。
3. ターンを進められる。
4. CPU が防衛メンバーを選択する。
5. CPU が遠征メンバーを選択する。
6. 自動戦闘によって勝敗が決まる。
7. 資金・アイテムを獲得する。
8. キャラクターが負傷することがある。
9. 遠征失敗によって虜囚になることがある。
10. 給料が発生する。
11. 忠誠度が変化する。
12. リーダーが行動不能なら新しいリーダーが決まる。
13. これらを簡単な UI または `Debug.Log` で確認できる。

## 20. 実装上の原則

- システムごとの責務を分離する。
- MonoBehaviour へのロジック集中を避ける。
- UI とゲームロジックを分離する。
- 戦闘ロジックと経営ロジックを分離する。
- CPU 判断を独立させる。
- ScriptableObject は設定データ中心に使用する。
- ランタイム状態とマスターデータを分離する。
- 後からセーブ・ロード可能なデータ構造を意識する。
- 数値は可能な限り Inspector または設定データから調整可能にする。
- 初期段階では過剰に複雑なアーキテクチャにしない。
- 外部ツールの停止や画像欠損でゲームロジックを停止させない。
- 既存コードがある場合は、構造と実装を確認してから変更する。

---

## 21. 最初の作業

最初に現在の Unity プロジェクトを確認し、Phase 1 の設計案を作成する。

設計案には次を含める。

1. 必要なクラス一覧
2. 各クラスの責務
3. データの流れ
4. フォルダ構成
5. Phase 1 の実装順序

設計を必要以上に巨大化させず、実際に動作する最小構成を優先する。設計後、その構成に沿って Phase 1 の実装を進める。

ComfyUI / WPF ツールは Phase 1 と切り離し、別の技術検証と実装計画として扱う。
